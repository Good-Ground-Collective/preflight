# preflight — layout, test placement and import hygiene rules

## Problem Statement

The same structural review comments keep coming back: a file in the wrong folder, a test in a
top-level `__tests__/`, a 600-line file that should be a folder, `../../` imports, `#private`
fields, comments hanging off Zod fields. Some frameworks lint a few of these for their own
modules, but nothing general does, so most TypeScript repos rely on review to catch them.

## Solution

Add eleven rules to preflight and a new opt-in `layout` config. These rules depend on the repo's
shape, so each repo configures its own folders.

Rules that only need the AST go into `go-no-go` or `recommended` as usual. Rules that read the
filesystem go into `layout` and are never on by default. This keeps "every preflight rule is a
pure AST check" true for the two existing configs.

A framework with its own layout conventions keeps its framework-specific checks as its own
rules, and ships a preset for `module-layout` instead of reimplementing the folder walk.

### New rules

| Rule | Config | Charter | What it does |
| --- | --- | --- | --- |
| `module-layout` | layout | M-15 | Folders follow module → role → concept. Configurable. |
| `test-location` | layout | M-17 | Tests sit in a `__tests__/` beside the code. No repo-level test tree. |
| `test-file-naming` | layout | M-17 | `<source>.test.ts` / `<name>.integration.test.ts`; no `.spec`. |
| `max-directory-entries` | layout | M-16 | A folder holding more than N source files has to be split into subfolders. |
| `no-upward-imports` | go-no-go | M-21 | No relative import that leaves the package root. |
| `no-parent-relative-imports` | recommended | M-21 | No `../`. Import across folders through a `#alias/` subpath. |
| `no-ecmascript-private` | go-no-go | M-22 | TypeScript `private`, never `#field`. |
| `filename-matches-export` | recommended | M-23 | A file's exported class is named for the file. |
| `no-schema-field-comments` | go-no-go | M-24 | No comments on `z.object` fields. Use `.describe()` / `.meta()`. |
| `no-env-outside-config` | recommended | M-25 | `process.env` is read only in the config files you name. |
| `no-comments` | recommended | M-2, M-14 | No comments except doc comments on declarations and tool directives. |

Stock rules added to `recommended`: `max-lines` (300, skipping blank lines and comments),
`max-lines-per-function` (60), and `@eslint-community/eslint-comments/require-description`.
`linterOptions.reportUnusedDisableDirectives: 'error'` goes into both configs.

### `module-layout`

A **module** is any folder the `module`
setting recognizes. Inside it, files sit in role folders, one folder per concept, nested to a
fixed depth. A folder that is itself recognized as a module is a submodule and follows the same
layout.

```js
'preflight/module-layout': ['error', {
  root: 'src',
  topLevel: {
    dirs: ['packages', 'config', 'db'],
    files: ['index.ts', 'server.ts'],
  },
  module: {
    marker: 'module.ts',       // default; a module is a folder holding a file matching this glob
    // or: match: 'src/packages/*/*'  — a module is a folder matching this path glob
  },
  moduleRoot: {
    files: ['module.ts', 'errors.ts'],
    dirs: ['contracts', '__tests__'],
  },
  roles: ['domain', 'models', 'services', 'definitions', 'repositories', 'loaders',
          'savers', 'transformers', 'resources', 'subscribers', 'exposures'],
  conceptFolders: true,          // role/<concept>/file.ts, never role/file.ts
  maxConceptDepth: 1,            // files sit directly in the concept folder (plus __tests__/)
}]
```

- **Outside any module**, only `topLevel.dirs` and `topLevel.files` may sit directly in `root`.
  This is the "acceptable top-level folders and files" check.
- **At a module root**, only `moduleRoot.files`, `moduleRoot.dirs`, `roles` and submodules may
  appear.
- **Inside a role**, `conceptFolders: true` requires `role/<concept>/<file>`. Set it to `false`
  for the lighter `models/` + `services/` + `definitions/` layout.
- **Messages** state the expected path (`Expected services/<concept>/schedule-builder.ts`), the
  so the fix is obvious.
- **Presets.** `preflight.layouts.module` (the full module → role → concept layout) and
  `preflight.layouts.slice` (slice → `models` / `services` / `definitions`, no concept folders).
  A framework can export its own preset that extends either one.
- The `marker` lookup reads the directory fresh for every file,
  so the rule stays correct in editor sessions.

### `test-location`

```js
'preflight/test-location': ['error', {
  style: 'tests-folder',            // or 'adjacent' (foo.ts + foo.test.ts side by side)
  forbiddenRoots: ['test', 'tests', 'src/__tests__'],
  allowedSubfolders: ['support', 'fixtures'],
}]
```

- `tests-folder`: every test file is in a `__tests__/` folder whose parent holds source code.
  There are no nested `__tests__/x/` folders other than `allowedSubfolders`.
- No test file under any of the `forbiddenRoots`.
- No non-test source file inside `__tests__/` other than the allowed subfolders.

### `test-file-naming`

```js
'preflight/test-file-naming': ['error', {
  suffixes: ['test', 'integration.test', 'e2e.test'],
  matchSource: 'concept',   // a test in a concept's __tests__/ is named for a source file beside it
}]
```

- Only the listed suffixes are allowed (so no `.spec.ts`).
- With `matchSource: 'concept'`, a unit test in `<concept>/__tests__/` must be named
  `<sibling>.<suffix>.ts`. A module-level `__tests__/` is exempt: that is where integration and
  cross-concept tests go, under any name.

### `max-directory-entries`

Default limit is 12 source files per folder, counting neither tests nor `__tests__/`. This nudges toward "wide and nested" without blocking normal folders.

### `filename-matches-export`

Each exported class must end with the PascalCase file name. `logger-binder.ts` may export
`PinoLoggerBinder`, because the implementation detail goes first. The
`groupingFiles` setting (default `['*-errors.ts', 'errors.ts', 'ids.ts']`) exempts files that
deliberately hold a family of classes, such as error hierarchies.

### `no-schema-field-comments`

Reports any comment attached to a property inside `z.object({...})`, `z.strictObject` or
`.extend({...})`. The message points to `.describe()` / `.meta()`, which flow into OpenAPI.

### `no-env-outside-config`

`process.env` and `import.meta.env` member access is reported outside the `allow` globs
(default `['**/config/**', '**/*.config.ts']`). It is in `recommended`, not `go-no-go`, because
scripts and tooling legitimately read env.

### `no-comments`

This rule reports every comment except two kinds:

1. **Doc comments on a declaration.** A `/** … */` block counts only when the next token starts
   a class, interface, type alias, function, enum, exported variable, class member, or interface
   or object-type property. A `/** */` left in the middle of a function body is reported, so doc
   syntax can't be used to slip a comment through.
2. **Directives.** These are line or block comments whose text starts with an allowed prefix.

```js
'preflight/no-comments': ['error', {
  allowPrefixes: [
    'eslint-disable', 'eslint-enable',        // lint suppressions
    '@ts-expect-error', '@ts-ignore',          // compiler suppressions
    'prettier-ignore', 'c8 ignore', 'v8 ignore', 'istanbul ignore',
    'SAFETY:',                                 // required by require-safety-comment-for-type-assertion
  ],
  additionalPrefixes: [],                      // e.g. 'raw-sql:' when another rule requires that annotation
}]
```

- Triple-slash `/// <reference …>` directives and shebangs are always allowed.
- `SAFETY:` counts only as the comment's prefix, and `require-safety-comment-for-type-assertion`
  is tightened to match, so a note that satisfies one rule always satisfies the other.
- `additionalPrefixes` exists for annotations that other lint rules require, such as a
  `// raw-sql: <reason>` escape hatch. Banning them would make the two rules fight. A plugin
  that requires annotations can export its prefix list for consumers to spread in.
- This rule also enforces the structural half of M-2 and all of M-14 (commented-out code). That
  makes `no-paragraph-comments` redundant inside `recommended`. It stays in `go-no-go` for repos
  that don't adopt `recommended`.
- **Migration cost.** Code that already avoids explanatory comments is nearly clean, since what
  remains is mostly directives. A codebase with heavy narrative commenting needs a bulk cleanup,
  or a temporary `files` override that turns the rule off for legacy paths and shrinks over time.
  This cost is why the rule sits in `recommended`, not `go-no-go`.

## Background

An agent follows a rule it is forced to follow far more reliably than one it is asked to follow.
Repo conventions belong in linters, not in files agents are asked to read. Every rule here comes
from a review comment that kept recurring:

- "In general I want my file hierarchies wide and nested."
- "We're looking for small, focused files here … very composable from a top level domain, down
  to sub-sub-sub-domains."
- "we hate top level `__tests__` directories, separate items by models, services, exposures,
  etc."
- "why does this test live in a top level `__tests__` directory, and is not colocated in the
  models directory with the code it is testing?"
- "we should use tsconfig aliases for all of these paths, across the whole repo"
- "why'd we start using the es6 private method instead of `private` from typescript?"
- "Zod fields should _not_ have inline comments. Any relevant details should live on the schema
  itself via the .meta/.describe methods"
- "create a zod schema that checks the process.env once"
- "this file is pretty big … better served if broken out into multiple files, underneath a parent
  folder"

## Technical Notes

- Filesystem rules use `context.filename` / `context.cwd` and `node:fs`. They never need
  `parserOptions.project`. Package root = nearest `package.json`.
- Each filesystem rule reports once per file on `Program`, at line 1.
- `max-directory-entries` reports only on the alphabetically first file in the folder, so one
  folder gives one error, not twelve.
- Options are validated with Zod in `create`.
- New peer dependency for `recommended`: `@eslint-community/eslint-plugin-eslint-comments`.

## Known Gaps and Edge Cases

- **Repos that keep tests beside their source** (`foo.ts` + `foo.test.ts`) either set
  `style: 'adjacent'` or migrate. The default is `tests-folder`.
- **Repos with a legacy top-level `test/` tree** fail `forbiddenRoots` until they migrate. Until
  then they add a per-repo `ignores` entry, not a rule change.
- **Config files and scripts** (`*.config.ts`, `scripts/**`) fall outside `root` and aren't
  checked by `module-layout`.
- **Not lintable, so left to the charter as Tier B judgment:** service names that describe a
  role, generic platform modules holding mechanism only, tests that re-prove what a linter or
  schema already guarantees, and committed plans or one-off scripts.
- **Left out on purpose.** These were raised as questions in review, not as rules: banning
  `readonly`, banning `satisfies`, and preferring `forEach` over `for…of`.
